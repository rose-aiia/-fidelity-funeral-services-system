# Backend integration

The app runs on built-in sample data today. This describes how it talks to a backend once there is one,
and what that backend has to provide.

## Modes

| `VITE_API_MODE` | Behaviour |
| --- | --- |
| `mock` (default) | Serves the built-in sample data. No network calls. Pages render immediately. |
| `live` | Calls the API at `VITE_API_BASE_URL` (default `/api`). Sections show a loading state, then data or an error with **Try again**. |

Copy `.env.example` to `.env.local` to change them. Vite bakes these in at build time, so a `live` build
needs `VITE_API_MODE=live` set when it is built. An unrecognised mode fails at startup.

In development, requests to `/api` are proxied to `API_PROXY_TARGET` (default `http://localhost:8080`, the
reference mock server) with the `/api` prefix removed, so the browser sees a single origin and no CORS setup
is needed. To proxy to the real backend instead, set `API_PROXY_TARGET=http://localhost:4000` (its default
`PORT`).

## Try it without a backend

```sh
npm run mock-api                          # reference server on :8080, built from the app's own data
echo VITE_API_MODE=live > .env.local
npm run dev
```

`scripts/mock-api.mjs` implements [`openapi.yaml`](./openapi.yaml). It adds 300ms of latency
(`MOCK_API_LATENCY_MS`) and `GET /__fail?on=1` to make every call return 503, for exercising error states.

## How the pieces fit

```
components  →  features/<x>/queries.ts  →  features/<x>/api.ts  →  lib/http.ts  →  fetch
                (React Query hooks)         (typed endpoint calls)   (errors, timeout)
```

- `lib/http.ts`: `get` / `post`. Adds JSON headers, a 10s timeout, and cancellation. Every failure
  becomes an `ApiError` with a `status` and `code` (`network_error`, `timeout` and `invalid_response` are
  generated by the client). Caller-initiated aborts are rethrown untouched.
- `lib/api-error.ts`: `getErrorMessage` maps an error to user-safe copy and never shows server text.
  `isRetryable` stops retries on 4xx (except 429).
- `features/<x>/api.ts`: one function per endpoint. This is the only place that knows about mock vs live.
- `features/<x>/queries.ts`: React Query hooks. In mock mode they are seeded with the sample data so pages
  render synchronously; in live mode there is no seed.

### Adding an endpoint

1. Add it to `docs/openapi.yaml` and to `scripts/mock-api.mjs`.
2. Add a typed function to the feature's `api.ts` with a mock branch and a `get`/`post` call.
3. Add a `queryOptions` + hook in `queries.ts` (or call the function directly for one-off writes, as
   `QuoteForm` does).
4. Render with `<QueryState>` for the not-loaded case.

## Authentication and accounts

Customers sign in with a Zimbabwean mobile number and a 6-digit SMS code. There are no passwords.

- **Session.** `POST /auth/signin` and `/auth/signup` set an `httpOnly`, `SameSite=Lax` cookie named `sid`
  (add `Secure` in production). The browser never sees the token; `http.ts` sends it with
  `credentials: 'same-origin'`. `POST /auth/signout` clears it.
- **401 handling.** `lib/http.ts` calls a registered handler on any `401`, and the auth provider uses it to
  drop the signed-in user, so an expired session returns the person to sign-in from any screen. Use code
  `unauthenticated` for a missing or expired session. Note that `otp_invalid` on the auth endpoints is
  also a `401`, but it happens before any session exists.
- **Lockout.** 5 failed code attempts for a phone number (wrong code on `/auth/signin` or `/auth/signup`)
  and 5 failed policy-link attempts for a user each produce `429` with code `locked_out`. A success resets
  the counter. Choose the lockout window on the backend; the mock never unlocks until it restarts.
- **Policy linking.** `POST /me/policy` matches policy number plus national ID number against the
  back-office record. ID numbers are only received and never sent to the browser.
- **Demo personas are mock mode only.** The login page's one-click personas call the in-browser mock store
  and are hidden in live mode. Live mode talks to the real endpoints below.

| Endpoint | Purpose | Notable errors |
| --- | --- | --- |
| `POST /auth/otp` | Send an SMS code | 422 `validation_failed`, 429 `locked_out` |
| `POST /auth/signin` | Sign in (200, sets cookie) | 401 `otp_invalid`, 404 `account_not_found`, 422, 429 |
| `POST /auth/signup` | Create account (201, sets cookie) | 401 `otp_invalid`, 409 `account_exists`, 422, 429 |
| `POST /auth/signout` | Clear the session (204) | |
| `GET /me`, `PATCH /me` | Read or update the profile | 401 `unauthenticated`, 422 |
| `GET /me/policy` | Linked policy, or 204 if none | 401 |
| `POST /me/policy` | Link a policy | 422 `policy_not_found`, 429 `locked_out` |
| `GET /me/requests` | Assistance requests, newest first, without the internal `assignment.note` | 401 |
| `POST /me/requests` | Create a request (201, status `received`) | 422 (`message` required for `general`, max 600) |

## Memorials

Public remembrance pages (biography, timeline, photos, virtual flowers and candles, a tribute wall). The
contract is in `openapi.yaml`; the mock implements all of it, with state in memory. Try it with
`+263771234567` (owns the published sample `/memorials/grace-nyathi`, which has one tribute awaiting approval).

| Endpoint | Purpose | Notable errors |
| --- | --- | --- |
| `GET /memorials/{slug}`, `GET .../tributes` | Public page and approved tributes | 404 `not_found` |
| `POST .../tributes` | Leave a tribute (201, `pending` for visitors, `approved` for the owner) | 404, 422, 429 `rate_limited` |
| `POST .../offerings` | Flower or candle, returns the new totals | 404, 422, 429 `rate_limited` |
| `GET`, `POST /me/memorials` | List (newest first) and create (unpublished) | 401, 422 |
| `GET`, `PATCH`, `DELETE /me/memorials/{id}` | Read, edit (including `published`) or delete | 401, 404, 422 |
| `POST`, `PATCH`, `DELETE /me/memorials/{id}/photos[/{photoId}]` | Add, caption, remove photos | 404, 422 `photo_limit` |
| `GET /me/memorials/{id}/tributes`, `PATCH .../{tributeId}` | Moderation queue; set `approved` or `removed` | 404, 422 |

- **Visibility.** `GET /memorials/{slug}` and its sub-resources work without a session. An unpublished
  memorial is visible only to its owner (a valid `sid` cookie is optional on the public routes and just
  identifies them). For anyone else it answers `404 not_found`, the same as a slug that doesn't exist, so
  drafts can't be discovered. On `/me/memorials/{id}` another user's memorial is also `404`, never `403`.
  The owner's identity is never in a response; `Memorial` carries no `ownerId`.
- **Moderation.** A visitor's tribute is stored `pending` and only shows publicly after the owner sets it to
  `approved`. The owner's own tributes are `approved` straight away. `removed` is final: the tribute leaves
  both lists and can't be changed again (keep the row server-side for audit if you need to).
- **Rate limits** answer `429` with code `rate_limited`: 5 tributes per memorial per visitor per hour, and 20
  offerings per memorial per visitor per day. The mock keys on the client IP in memory. A real backend should
  key on a trusted client IP (not a spoofable `X-Forwarded-For`) and/or a visitor cookie, and add a
  CAPTCHA or similar if tribute spam appears.
- **Photo upload is interim.** `POST .../photos` takes a base64 `data:` URL in JSON (JPEG, PNG, WebP or SVG,
  about 1.5 MB at most, 8 photos per memorial) and stores it as the photo's `url`. That is only fit for the
  mock. Production needs multipart or pre-signed uploads to object storage, server-side resizing and
  re-encoding (strip EXIF and GPS), content scanning for malware and abusive images, size and type checks on
  the bytes rather than the declared type, and a hosted CDN `url` in the response. Treat SVG as untrusted
  (sanitise it, or drop it from the allowed types).
- **Abuse and safety.**
  - Tributes are plain text; escape on render and never trust `message`.
  - The family needs a takedown path beyond the API: a way for them (or the funeral home) to unpublish or
    delete a memorial and remove any tribute quickly, plus a way for the public to report one.
  - Unpublished memorials must not be indexed: don't list them anywhere public, leave them out of the
    sitemap, and send `noindex` on their pages. Consider `noindex` for published ones too unless the family
    opts in to search visibility.
  - Memorials of private individuals are sensitive: audit who creates, edits and removes them.

## Marketplace and orders

A catalogue of products and services, a cart in the browser, and checkout with EcoCash or Paynow. The
contract is in `openapi.yaml`; the mock implements all of it. The order lifecycle itself (`order-flow.ts`)
is shared by the browser mock and `mock-api.mjs`, so both behave the same. Try it as `+263771234567`, who
has two seeded orders (`FS-1017` delivered, `FS-1038` in progress).

| Endpoint | Purpose | Notable errors |
| --- | --- | --- |
| `GET /marketplace/items`, `GET .../{id}` | Public catalogue and one item | 404 `not_found` |
| `GET /me/orders`, `GET /me/orders/{id}` | The user's orders (newest first), brought up to date on read | 401, 404 |
| `POST /me/orders` | Place an order and start payment (201, `awaiting_payment`) | 422 (keys `delivery.*`, `payment.*`, `lines`, `lines.<n>`), 429 `rate_limited` |
| `POST /me/orders/{id}/payment` | New payment attempt after a failure, or another method | 404, 409 `order_not_payable`, 422 |

- **The server owns the price.** A new order carries item ids, chosen option ids, quantities and
  personalisation text, never prices. The server looks every item up and computes unit prices, line totals,
  the delivery fee and the total (`features/marketplace/pricing.ts`, which the browser uses only for a
  preview). Unknown items, options the item doesn't offer, a quantity outside 1 to 10, missing or surplus
  personalisation and more than 20 lines are rejected. Prices are copied onto the order, so a later catalogue
  change doesn't alter it.
- **Delivery fee.** A flat $25 once per order when any line is `delivery`; orders of `service` items only
  (repatriation, marquee hire, video tribute) pay none.
- **Order status:** `awaiting_payment` -> `paid` -> `confirmed` -> `in_progress` -> `delivered`. A failed
  payment gives `payment_failed`; a new attempt returns it to `awaiting_payment`. `cancelled` exists in the
  type but nothing produces it yet.
- **Payment status:** `pending` -> `paid` or `failed`. `Order.payment` is the latest attempt; its reference
  is `<order reference>-P<attempt>`. Only `awaiting_payment` and `payment_failed` orders can be paid
  (otherwise 409), so a paid order can't be charged twice.
- **Mock timings.** An EcoCash prompt is answered 4 seconds after it starts. A paid order becomes `confirmed`
  20 seconds after payment, `in_progress` after 60 and `delivered` after 150 (about 2.5 minutes in all). Orders
  are advanced whenever they are read; nothing runs in the background. EcoCash `0780000000` is always
  declined (demo behaviour of the mock server only); any other 077 or 078 number pays. Seeded orders don't move.
- **Paynow in the mock** settles by itself after 4 seconds, like EcoCash, because the mock has no hosted
  Paynow page. This is mock-only. In production `POST /me/orders` (or the payment endpoint) would return a
  redirect URL for Paynow's hosted page, the result would arrive by webhook, and `GET /me/orders/{id}` stays the
  source of truth. The response has no redirect field yet; add one when the integration is built.
- **Rate limit.** 10 orders per user per hour, `429` `rate_limited`, counted only for valid orders. The mock
  keeps it in memory; a real backend should also limit payment attempts per order.
- **Ownership.** Another user's order is `404`, never `403`.
- **A real payment integration needs:**
  - EcoCash and Paynow merchant credentials and integration keys, kept server-side.
  - Webhook endpoints that verify the provider's signature (Paynow's hash), reject replays and update the
    order idempotently. Never trust the browser's claim that a payment succeeded.
  - An idempotency key on `POST /me/orders` (for example an `Idempotency-Key` header), so a double tap or a
    retry after a timeout doesn't create two orders or two charges.
  - Reconciliation against provider statements, and a path for payments that arrive after the order was
    abandoned or paid another way.
  - Refunds and cancellations (the `cancelled` status), with an audit trail.
  - Payment timeouts: an unanswered EcoCash prompt should expire to `failed` rather than stay `pending`.
- **Provider fulfilment.** Each line names its `provider`. Orders placed through the API still move through
  `confirmed`, `in_progress` and `delivered` on a timer until a person steps in; providers and administrators
  then move them with `PATCH /admin/orders/{id}` (see [Staff portal](#staff-portal)), which stops the timer for
  that order. The timer is a demo convenience and goes away in production.
- **Switched-off providers.** `GET /marketplace/items[/{id}]` leaves out products whose provider an administrator
  has switched off, and `POST /me/orders` prices against that same list, so a stale basket line fails with the
  existing `422` "no longer available".
- **Images.** `MarketplaceItem.image` is a URL in production. The mock server returns inline `data:` URIs.

## Staff portal

Administrators triage assistance requests, hand them to funeral service providers, and manage customers,
orders and providers. Providers (funeral directors and marketplace vendors) see only what concerns them. The
contract is the `/admin/*` group in `openapi.yaml`; the mock implements all of it. The rules themselves
(`features/admin/logic.ts`, `features/account/request-flow.ts`, `ORDER_TRANSITIONS` in `order-flow.ts`) are
pure functions shared with the browser mock, so a real backend can port them one for one. Try it with the
three staff numbers in the table above.

| | Customer | Provider | Administrator |
| --- | --- | --- | --- |
| Own requests, orders, memorials (`/me/*`) | yes | no | no |
| Requests and the internal note | own, no note | only those assigned to them, with the note | all, with the note |
| Assign a request | no | no | yes |
| Accept, decline, complete an assignment | no | their own | complete only |
| Orders | own | only orders with their products, their lines and share only | all |
| Move an order along | no | wholly-theirs orders, not cancelling | any legal move, including cancelling and shared orders |
| Customers, providers, activity log | no | no | yes |
| Switch a provider on or off, add one | no | no | yes |

| Endpoint | Who | Notable errors |
| --- | --- | --- |
| `GET /admin/overview` | admin, provider | |
| `GET /admin/requests[?status=]`, `GET .../{id}` | admin (all), provider (theirs) | 404 for a provider on someone else's |
| `POST /admin/requests/{id}/assignment` | admin | 409 `provider_inactive`, `already_complete`, 422 `providerId` |
| `PATCH /admin/requests/{id}/assignment` | provider (own), admin (`completed` only) | 403, 404, 409 `invalid_transition` |
| `GET /admin/orders[?status=]`, `PATCH .../{id}` | admin (all), provider (theirs) | 403, 404, 409 `invalid_transition` |
| `GET /admin/customers[/{id}]` | admin | 404 |
| `GET`, `POST /admin/providers`, `PATCH .../{id}` | admin | 409 `provider_exists`, 422, 404 |
| `GET /admin/activity` | admin | |

- **Authorise on the server, every time.** Take the role and `providerId` from the session's user record, never
  from the request (a body, header or query string that says "I am a provider" must be ignored). Scope every
  query by `providerId` in the data layer (`WHERE assignment.providerId = :mine`), not by filtering after the
  fact, and rebuild `actions` on the server from the same rules; the client only uses them to show buttons.
  - `401` no session. `403` signed in but this role may never do this (a customer on `/admin`, a provider on an
    administrator route, an administrator accepting a request on a provider's behalf, a provider on a shared
    order or cancelling). `404` the caller may not even know it exists (a provider asking for a request or order
    that isn't theirs), so ids can't be probed. A legal order move the caller isn't allowed to make is `403`; a
    move that isn't legal from the current status is `409` for everyone.
  - Re-check on every write, not just on read, and load the row inside the same transaction as the update.
- **Privacy: show providers only what they need.** A provider sees a request's message, contact preference and
  the customer's name and phone, never the customer's policy, policy number or status. On orders they see only
  their own lines and their share of the money (no other providers' lines, no delivery fee), plus the delivery
  contact they need to deliver. Customer detail (policy, other requests, memorials, total spend) is
  administrator-only, and the policy's ID number never leaves the server for anyone.
- **The internal note stays internal.** `assignment.note` is the administrator's note to the provider. It is
  in `/admin` responses and nowhere in `/me/*`: strip it in one place (a customer-facing serialiser) rather
  than hoping each endpoint remembers. Families see the assignment's provider, status and times only.
- **Assignment lifecycle.** `POST` assign: request `received`/`assigned`/`in_progress` -> `assigned`, assignment
  `assigned` (assigning again replaces it; a `complete` request is `409`; an inactive provider is `409`).
  The provider then answers: `assigned` -> `accepted` (request `in_progress`) or `declined` (request back to
  `received`, `assignedTo` cleared, and a bereavement becomes urgent again for the administrator).
  `accepted` -> `completed` (request `complete`). Nothing else is legal (`409 invalid_transition`). An
  administrator may close any open request with `completed`. Keep a declined assignment as history; don't
  delete it.
- **Audit log.** Every mutation by an administrator or provider writes an entry in the same transaction as the
  change: who (user and role), what (action, entity type and id, readable `summary`) and when (server time).
  The log is append-only: no update or delete endpoint, and the database role used by the API gets `INSERT`
  and `SELECT` only. `summary` is for people ("Assigned AR-1051 to Harare Funeral Care"); keep the structured
  facts (previous and new value, IP address) in `detailsJson` as well. Also log repeated `403`s, since they point
  at probing. `GET /admin/activity` returns the latest 100, newest first.
- **Deactivating a provider** takes effect at once: new assignments are refused, their products leave the
  catalogue and can't be priced into new orders. Existing assignments and orders are left alone so staff can
  finish them (a switched-off provider's staff can still sign in and complete what they hold).

How these shapes map to the backend's Prisma models (`funeral-service-backend/prisma/schema.prisma`), and what
the schema still needs:

| API | Prisma | Notes |
| --- | --- | --- |
| `Role` `customer` / `admin` | `UserRole` `CUSTOMER` / `ADMIN` | Add `PROVIDER` (and `STAFF` if kept). |
| `User.providerId` | none | Add a nullable `providerId` on `User` (or a `ProviderStaff` join table) pointing at `FuneralServiceProvider`. |
| `User` signs in by phone + SMS code | `User.email` + `passwordHash` | The schema is email and password; add `phone` and an OTP flow, or change the app. |
| `ProviderRecord` | `FuneralServiceProvider` | `isActive` maps directly. `phone` is `phoneNumber`, `province` and `city` exist; add a slug (`id` here is `providerIdFor(name)`) or map by uuid. `addressLine1` and `country` are required in the schema but not collected. |
| `AssistanceRequest` | `FuneralAssistanceRequest` | Status differs, see below. Add `kind` (bereavement / claim / general), `contactPreference`, and a human reference (`AR-1042`). |
| `RequestAssignment` | `ProviderAssignment` (`assignmentType` `ASSISTANCE`) | `providerId`, `assignedAt` and `notes` (the internal note) map directly; `assignedByAdminId` is required. Add `respondedAt`. Current assignment = latest row for the request. |
| `AssignmentStatus` `assigned` / `accepted` / `declined` / `completed` | `AssignmentStatus` `ASSIGNED` / `ACCEPTED` / `DECLINED` / `COMPLETED` | Same four. `CANCELLED` isn't used by the app. |
| `RequestStatus` `received` / `assigned` / `in_progress` / `complete` | `AssistanceStatus` `OPEN` / `REVIEWED` / `SCHEDULED` / `COMPLETED` / `CANCELLED` | Not the same set. Either derive the app status from the latest assignment (`statusForAssignment`) and keep `AssistanceStatus` for the back office, or add the missing values. |
| `AuditEntry` | `AuditLog` | `action` `create` / `update` / `assign` -> `AuditActionType` `CREATE` / `UPDATE` / `ASSIGN`. `entityType` + `entityId` exist; `actorName` / `actorRole` come from the actor relation; `summary` goes in `detailsJson`. `actorAdminId` only covers administrators: providers need `actorUserId` (already there). |
| `Order` | `MarketplaceOrder` + `OrderItem` | The schema has no per-line provider, delivery contact, payment or events. Add `MarketplaceProduct.providerId`, copy it and the product name onto `OrderItem`, and add delivery fields, a `Payment` model and an order event table. |
| `OrderStatus` | `OrderStatus` | See below. |
| `MarketplaceItem` hidden when provider off | `MarketplaceProduct.isActive` | Filter by the provider's `isActive` as well as the product's. |

`OrderStatus` differs between the two. The app has `awaiting_payment`, `payment_failed`, `paid`, `confirmed`,
`in_progress`, `delivered`, `cancelled`; Prisma has `PENDING`, `PAID`, `PROCESSING`, `SHIPPED`, `CANCELLED`,
`COMPLETED`. Reasonable mapping: `awaiting_payment` / `payment_failed` -> `PENDING` (the payment state lives on a
`Payment` row, which the schema lacks), `paid` -> `PAID`, `confirmed` / `in_progress` -> `PROCESSING`,
`delivered` -> `COMPLETED`, `cancelled` -> `CANCELLED`. That collapses `confirmed` and `in_progress` and has no
use for `SHIPPED`, and `payment_failed` can't be told from "not paid yet". Cleaner: add `AWAITING_PAYMENT`,
`PAYMENT_FAILED`, `CONFIRMED`, `IN_PROGRESS` and `DELIVERED` to the enum (or store the app's seven values) and
keep the transitions in `ORDER_TRANSITIONS`, which the server must enforce.

## What the backend must do

- **Own the price.** `POST /quote-requests` receives choices only and returns the authoritative
  `estimatedTotal`. The browser's estimate is a preview. The surcharge tables in
  `features/plans/pricing.ts` duplicate backend rules, so they will drift unless the backend exposes them
  (for example `GET /pricing-rules`) and the app reads them.
- **Return `{ code, message, details? }` for every error**, with the right status (422 for validation,
  429 for rate limits). The app shows its own copy; `message` is for logs.
- **Serve the SPA with a fallback.** Routes like `/provider-portal` are real paths, so the host must return
  `index.html` for unknown paths. The dev and preview servers already do.
- **Handle the `/api` prefix.** Dev proxies strip it. In production either mount the API at `/api` and set
  `VITE_API_BASE_URL=/api`, or point `VITE_API_BASE_URL` at the API's absolute URL and enable CORS for the
  site's origin.

## Not wired yet: decisions needed

- **Quote requests have no contact details.** The form collects service type, town and plan only, so a
  provider has no way to reach the family. This needs name and phone at minimum, plus consent wording.
  The contract does not include them yet because the UI doesn't collect them.
- **Staff portal roles.** The app's role guard only hides screens. The `/admin` endpoints enforce roles
  themselves (see [Staff portal](#staff-portal)); the `staff` role exists in the type but has no portal
  behaviour yet, so the mock answers `403` for it. Decide what `staff` should be, or drop it.
- **Marketplace "Enquire" button** does nothing yet and needs an endpoint.
- **Response validation.** Responses are cast to their TypeScript types. A schema library (e.g. Zod) at the
  `api.ts` boundary would catch contract drift at runtime; it wasn't added to keep dependencies minimal.
- **Marketplace `accent`** is a decorative glyph, a fallback for items without an `image`.
